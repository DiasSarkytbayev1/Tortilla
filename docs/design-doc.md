## 1. Problem Statement

The Restaurant Chain Analytics Platform PRD (v0.2) defines a system that pulls bills from per-restaurant POS APIs, normalizes them, and lands them in PostgreSQL. The PRD specifies M3 as "Analytics dashboard — three core views: best sellers, peak hours, restaurant comparison."

The PRD names those three views but does not specify what is actually on each screen: which charts, which KPIs, which filters, which aggregations, what the layout looks like, what queries the backend runs, or how empty/loading/error states behave. This document fills that gap.

Scope is the **analyst dashboard only** (PRD §3 — analysts and executives). The operations dashboard (connector health, sync run history) is out of scope and will be designed separately.

---

## 2. Demand Evidence

The PRD §1 states three concrete questions that go unanswered today: "what's our best-selling dish?", "when do we get hammered on Saturdays?", and "how does Restaurant A compare to Restaurant B?". These are not hypothetical — they are listed as the founding motivation for building the platform. The analyst dashboard exists to make those three questions answerable in seconds rather than via manual work.

For a university project, demand is constructed (no real chain operates here), but the question shapes are real, well-known to anyone who has worked in restaurant ops, and map cleanly to standard chain BI workloads (Toast, Lightspeed, Square all ship analogous views).

---

## 3. Status Quo

Per PRD §1 and §3: today, "questions like 'what's our best-selling dish?' require manual work or go unanswered". The existing workaround is a per-restaurant Excel/CSV pull (the repo already contains a CSV generator under `tortilla_shops_reports/`), with HQ analysts manually consolidating across locations. The cost is analyst time and lag — by the time numbers are assembled, the week is over.

---

## 4. Target User & Scope

**Primary user:** HQ analyst. Comes to the dashboard with a question. Wants the answer in under 30 seconds. Slices by date range, restaurant, and category. Exports CSVs for executives.

**Secondary user:** Executive. Lands on the overview, scans five KPIs, leaves. Comes back next week to compare to last week.

**Out of scope for this design:**
- Restaurant managers (PRD §3 explicitly removes them as V1 users)
- Customer-facing surfaces
- Forecasting, ML, anomaly detection
- Profit / gross margin (the schema has no `cost` column — see §5)
- Multi-currency
- Native mobile apps

## 5. Constraints

These are inherited from the PRD and dictate what the dashboard can and cannot do.

| Constraint | Source | Implication for dashboard |
|---|---|---|
| Schema is fixed (PRD §6) | PRD §6, §12 | All metrics computed from `bills` + `bill_items` + `menu_items` + `restaurants`. No new columns. |
| `bills` has composite PK `(restaurant_id, bill_no)` plus surrogate UK `id` | PRD §6 ER diagram | All joins from `bill_items` use `bill_items.bill_id = bills.id` (the UK), since `bill_items.bill_id BIGINT` is a single-column FK. Every SQL query in this doc follows that convention. |
| **No cost / COGS in schema** | PRD §6 — `menu_items` has `price`, no `cost` | "Money" metric throughout the dashboard is **revenue (turnover)**, not profit. Every label says "revenue" or "turnover", never "profit". |
| `bill_items.unit_price` captured at sale time | PRD §6 design notes | Revenue is historically accurate even if `menu_items.price` changes later. We always sum `line_total` from `bill_items`, never recompute from `menu_items.price`. |
| **`bills.total` is the source of truth for whole-bill revenue** | This design doc decision (PRD does not pin it down) | KPIs that aggregate at the **bill** level (chain revenue, AOV, comparison totals) use `SUM(bills.total)` and `AVG(bills.total)`. KPIs that aggregate at the **item** level (Best Sellers, category breakdowns) use `SUM(bill_items.line_total)`. The two should reconcile within rounding; if they don't, that's an adapter bug to fix upstream — not a dashboard problem. |
| Single currency, currency symbol from config | PRD §2 non-goals | One currency, displayed using a single `CURRENCY_SYMBOL` config value (V1 default `€`). No FX, no per-restaurant currency. |
| Times are UTC in DB; display in chain timezone | PRD §10 (open question on TZ); PRD §6 uses `timestamptz` | All hour-of-day / day-of-week aggregations need a fixed display timezone. We use a single chain TZ stored in config (V1 default: `Europe/Madrid` — change per chain). |
| ~5,000 bills/day chain-wide | PRD §8 | One year ≈ 1.8M bills, 9M line items. Sub-second queries are achievable with the indexes already specified in PRD §8. No materialized views needed in V1. |
| Read-only API | PRD §2, §5 | Dashboard never writes. |
| Auth required for all endpoints | PRD §8 | Every dashboard route is gated by login. Auth scheme itself (session cookie vs JWT) is owned by the API service per PRD §5 — out of scope for this dashboard design; the dashboard just sends whatever credential the API service expects. |
| React + Recharts (proposed) | PRD §5 tech stack | Charts must be expressible in Recharts primitives (bar, line, area, pie, scatter, plus a custom SVG heatmap). |
| p90 query latency < 2s | PRD §8 | Performance budgets in §10 below. |

## 6. Premises

These are the assumptions this design rests on. If any one is wrong, parts of the design collapse and need revising.

1. **The PRD's data model is sufficient for V1 analytics.** All five views below can be built from `bills` + `bill_items` + `menu_items` + `restaurants` joined on existing FKs. No new tables.
2. **Profit is not a V1 metric.** "Money" everywhere means revenue (sum of `line_total`). Confirmed with project owner 2026-05-04.
3. **Analysts share a global view.** No per-restaurant access restriction (PRD §8). Every analyst sees every restaurant.
4. **Hourly sync latency is acceptable for analytics.** Dashboards show data that is up to ~90 minutes stale (per PRD §7's 90-minute overlap window). This is fine for chain analytics; it would not be fine for live operations.
5. **A single chain timezone is good enough for V1.** Even if restaurants are in different cities, the chain has one HQ TZ for reporting purposes. Per-restaurant TZ rendering is V2.
6. **Date range is the dominant filter.** Every page is rendered "for a date range". Date range is global, persists across pages, and defaults to "last 7 days".
7. **Recharts can express every chart we need.** The only non-trivial chart is the day-of-week × hour-of-day heatmap; Recharts has no native heatmap, so we build it as a custom 7×24 SVG component (see §9.4). All other charts (bar, line, horizontal bar, multi-series line) are first-class Recharts primitives.

## 7. Approaches Considered

### Approach A: Overview + drilldowns (CHOSEN)

One landing "Overview" page with KPI cards and a chain-wide trend, plus four drilldown pages: Best Sellers, Time Series, Peak Hours, Restaurant Comparison. Global filter bar (date range, restaurants, categories) persists in URL across pages.

| | |
|---|---|
| Effort | M (~3 weeks per PRD M3) |
| Risk | Low |
| Pros | Analysts get synthesis (overview) AND deep dives (drilldowns); filter state persists; matches how Toast/Lightspeed analytics surfaces work; KPI overview is what executives actually use. |
| Cons | One more page than the PRD literally specifies; slightly more frontend work. |
| Reuses | Existing schema unchanged; CSV generator can power export buttons. |

### Approach B: Three flat pages (PRD-literal)

Exactly the three pages M3 names: `/best-sellers`, `/peak-hours`, `/comparison`. No overview, no time-series page (it's split between best-sellers and peak-hours).

| | |
|---|---|
| Effort | S (~2 weeks) |
| Risk | Low |
| Pros | Smallest scope; literally what the PRD says. |
| Cons | No synthesis view — every analyst session starts from a blank page; bills-over-time is awkwardly shoe-horned into one of the three pages; comparison page has to re-introduce KPIs that an overview would already have computed. |

### Approach C: Question-driven

Pages organized by analyst question rather than dimension: "What's selling?", "When are we busy?", "Who's leading/lagging?".

| | |
|---|---|
| Effort | M |
| Risk | Med |
| Pros | More user-centric vocabulary. |
| Cons | Diverges from PRD vocabulary, makes onboarding harder, doesn't actually change which charts are needed — just renames the routes. |

### Recommended approach

**Approach A: Overview + drilldowns.** It absorbs everything Approach B has, gives executives a default landing experience, and the drilldown pages map 1:1 to the PRD's three views (with one extra: a dedicated Time Series page, which is implicit in the PRD's "bill volume and revenue by hour of day" requirement F8 plus daily/weekly trend questions analysts will obviously ask).

## 8. Information Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Tortilla Analytics            [user ▾]  [Sign out]         │
├─────────────────────────────────────────────────────────────┤
│  GLOBAL FILTERS  [Last 7 days ▾]  [All restaurants ▾]       │
│                  [All categories ▾]  [Reset]                │
├─────────────────────────────────────────────────────────────┤
│  Overview │ Best Sellers │ Time Series │ Peak Hours │       │
│           │              │             │  │ Comparison      │
└─────────────────────────────────────────────────────────────┘
```

**Five pages:**
1. `/` — Overview (landing)
2. `/best-sellers` — top menu items
3. `/time-series` — revenue and bills over time
4. `/peak-hours` — when is each restaurant busy
5. `/comparison` — restaurant vs restaurant

**Global filter bar** is shown on every page. Filter state lives in the URL query string (`?from=2026-04-27&to=2026-05-04&r=1,2,5&cat=mains,drinks`) so any view is shareable as a link.

**Defaults:** date range = last 7 days; restaurants = all; categories = all.

**Filter applicability matrix** — not every filter applies to every view, since some KPIs are bill-level (no item info available without joining `bill_items`) and some are item-level. This is spelled out explicitly so the implementer doesn't have to guess.

| View | Date range | Restaurant | Category |
|---|---|---|---|
| Overview KPIs (revenue, bills, AOV, peak hour) | applies | applies | **ignored** — these are bill-level metrics |
| Overview KPI: top item | applies | applies | applies |
| Overview revenue trend | applies | applies | ignored |
| Best Sellers | applies | applies | applies |
| Time Series | applies | applies | ignored — switch to Best Sellers if you want category cuts |
| Peak Hours | applies | applies | ignored |
| Comparison | applies | applies (this **is** the dimension being compared) | ignored |

When `category` is set in the URL but doesn't apply to the current view, the filter chip is shown greyed-out with tooltip "Category doesn't affect this view". This prevents the analyst from setting category on Best Sellers, navigating to Time Series, and being silently confused.

**URL encoding rule for "all":** `r` and `cat` query params are *omitted* when "all" is selected, never sent as `r=all` or `r=`. The backend treats a missing `restaurants` param as "all restaurants", a missing `categories` param as "all categories". `r=` (empty) is invalid and rejected with 400.

## 9. Page-by-page Design

For each page below: wireframe → what it shows → chart specs → SQL.

### 9.1 Overview (`/`)

**Wireframe:**

```
┌──────────────────────────────────────────────────────────────┐
│  Overview — Last 7 days, all restaurants                     │
├──────────────────────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐       │
│ │ Revenue│ │ Bills  │ │ Avg    │ │ Top    │ │ Peak   │       │
│ │ €X     │ │ N      │ │ ticket │ │ item   │ │ hour   │       │
│ │ ▲ 12%  │ │ ▲ 8%   │ │ €Y     │ │ Pad T. │ │ 13:00  │       │
│ │ vs prev│ │ vs prev│ │ ▼ 2%   │ │ 1,240  │ │ 420    │       │
│ │  7d    │ │  7d    │ │ vs prev│ │ sold   │ │ bills  │       │
│ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘       │
├──────────────────────────────────────────────────────────────┤
│  Revenue trend (daily, chain-wide)                           │
│  ┌──────────────────────────────────────────────────┐        │
│  │           ╱╲                                     │        │
│  │      ╱╲  ╱  ╲   ╱╲                               │        │
│  │   ╱─╯  ╲╱    ╲─╯  ╲                              │        │
│  │  €0    Mon Tue Wed Thu Fri Sat Sun               │        │
│  └──────────────────────────────────────────────────┘        │
├──────────────────────────────────────────────────────────────┤
│  Quick links:                                                │
│   → Top 10 best sellers   → Peak hours heatmap               │
│   → Compare restaurants   → Daily revenue breakdown          │
└──────────────────────────────────────────────────────────────┘
```

**KPI cards (5):**
1. **Revenue** — `SUM(bills.total)` for the period. Currency formatted.
2. **Bills** — `COUNT(bills)` for the period.
3. **Avg ticket** (AOV) — defined as **mean** of `bills.total` (`AVG(bills.total)`), not median. Currency formatted.
4. **Top item** — menu item with highest sum of `bill_items.quantity` for the period (ties broken by lower `menu_items.id` for deterministic ordering). Shows item name + quantity sold.
5. **Peak hour** — hour-of-day (chain TZ) with most bills. Shows the hour in `HH:00` format + bill count.

Each card shows absolute value plus % change vs the immediately preceding period of the same length (last 7 days vs the 7 days before that). Up-arrow green for positive, down-arrow red for negative on revenue/bills/AOV; for "Top item" and "Peak hour" the change indicator is the *change in identity* ("was Tom Yum last period").

**"vs previous period" caveat:** comparing arbitrary 7-day windows can mislead because of day-of-week effects (Mon-Sun vs Wed-Tue is not apples to apples). For V1, we accept this — it's how every BI tool handles it. Document the convention in a tooltip on the delta indicator: "vs previous N-day period of the same length, ending the day before this period started." V2 could add "vs same period last week / last year" presets.

**Chart:** chain-wide revenue line, x-axis = day, y-axis = revenue. Recharts `<LineChart>` with a single `<Line>`, smooth interpolation off (`type="linear"`), grid on.

**SQL:**

```sql
-- KPI: total revenue, bill count, AOV for the period
-- Note: category filter is intentionally ignored on bill-level KPIs (see §8 filter matrix)
SELECT
  COUNT(*)        AS bills,
  SUM(b.total)    AS revenue,
  AVG(b.total)    AS avg_ticket
FROM bills b
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids);

-- KPI: top-selling item by quantity (returns one row)
-- Tie-break: lower menu_items.id wins, so the result is deterministic across runs
SELECT m.id, m.name, SUM(bi.quantity) AS qty
FROM bill_items bi
JOIN bills b      ON b.id = bi.bill_id   -- bill_items.bill_id → bills.id (UK)
JOIN menu_items m ON m.id = bi.menu_item_id
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
  AND (:categories IS NULL OR m.category = ANY(:categories))
GROUP BY m.id, m.name
ORDER BY qty DESC, m.id ASC
LIMIT 1;

-- KPI: peak hour (hour-of-day with most bills, in chain TZ)
SELECT EXTRACT(HOUR FROM b.sold_at AT TIME ZONE :chain_tz)::int AS hour,
       COUNT(*) AS bills
FROM bills b
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
GROUP BY 1
ORDER BY bills DESC, hour ASC   -- tie-break: earlier hour wins
LIMIT 1;

-- Chart: daily revenue trend
SELECT (b.sold_at AT TIME ZONE :chain_tz)::date AS day,
       SUM(b.total) AS revenue
FROM bills b
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
GROUP BY 1
ORDER BY 1;
```

The "vs previous period" deltas are computed by running the same KPI queries again with `:from` and `:to` shifted back by `(to - from)`.

### 9.2 Best Sellers (`/best-sellers`)

**Wireframe:**

```
┌──────────────────────────────────────────────────────────────┐
│  Best Sellers — Last 7 days, all restaurants, all cats       │
├──────────────────────────────────────────────────────────────┤
│  Rank by:  [• Quantity   ◯ Revenue]      Show: [Top 20 ▾]    │
├──────────────────────────────────────────────────────────────┤
│  ┌────────────────────────────────────────────────────┐      │
│  │ Pad Thai            ████████████████████  1,240    │      │
│  │ Tom Yum Soup        ███████████████       980      │      │
│  │ Green Curry         █████████████         820      │      │
│  │ ...                                                │      │
│  └────────────────────────────────────────────────────┘      │
├──────────────────────────────────────────────────────────────┤
│  # │ Item          │ Cat   │ Qty   │ Revenue │ % of total    │
│  1 │ Pad Thai      │ Mains │ 1,240 │ €18,600 │ 14.2%         │
│  2 │ Tom Yum Soup  │ Soups │   980 │ €11,760 │  9.0%         │
│  ...                                              [Export ▾] │
└──────────────────────────────────────────────────────────────┘
```

**Top section: ranked horizontal bar chart.** Recharts `<BarChart layout="vertical">`. X-axis = the chosen metric (qty or revenue). One bar per item, sorted descending. Top N selectable: 10 / 20 / 50 / 100.

**Bottom section: data table.** Columns: rank, item name, category, qty, revenue, % of total revenue. Sortable on every column. Sticky header. CSV export button (uses the existing `tortilla_shops_reports/` generator pattern).

**SQL:**

```sql
SELECT
  m.id,
  m.name,
  m.category,
  SUM(bi.quantity)   AS qty,
  SUM(bi.line_total) AS revenue,
  -- pct_of_total uses a windowed sum over ALL groups returned by the GROUP BY
  -- (i.e. percentage of the total revenue for items matching the filters,
  -- BEFORE the LIMIT is applied). This is the standard "share of category" semantics.
  ROUND(
    100.0 * SUM(bi.line_total) /
    NULLIF(SUM(SUM(bi.line_total)) OVER (), 0),
    2
  ) AS pct_of_total
FROM bill_items bi
JOIN bills b      ON b.id = bi.bill_id   -- bill_items.bill_id → bills.id (UK)
JOIN menu_items m ON m.id = bi.menu_item_id
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
  AND (:categories IS NULL OR m.category = ANY(:categories))
GROUP BY m.id, m.name, m.category
-- Single CASE expression so :rank_by switches the *one* sort key.
-- (Two separate CASE expressions would put NULL on the inactive branch
--  and cause every row to tie on the first key — bug, don't do it.)
ORDER BY
  CASE
    WHEN :rank_by = 'quantity' THEN SUM(bi.quantity)::numeric
    WHEN :rank_by = 'revenue'  THEN SUM(bi.line_total)::numeric
  END DESC,
  m.id ASC                       -- deterministic tie-break
LIMIT :top_n;
```

**Indexes needed:**
- `bills(restaurant_id, sold_at)` — already in PRD §8.
- `bill_items(bill_id)` — PostgreSQL does **not** auto-index FK columns. Add explicitly (see §10.4).
- `bill_items(menu_item_id)` — same reason. Add explicitly.
- `menu_items(category)` — speeds up the `m.category = ANY(...)` predicate.

### 9.3 Time Series (`/time-series`)

**Wireframe:**

```
┌──────────────────────────────────────────────────────────────┐
│  Time Series — Last 30 days, all restaurants                 │
├──────────────────────────────────────────────────────────────┤
│  Granularity: [Hour ◯  Day •  Week ◯  Month ◯]               │
│  Metric:      [• Revenue   ◯ Bills   ◯ Avg ticket]           │
│  Overlay:     [☑ Show previous period for comparison]        │
├──────────────────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────────────┐        │
│  │  €  ╱╲          ╱╲    ╱╲                         │        │
│  │    ╱  ╲    ╱╲  ╱  ╲  ╱  ╲   (this period)        │        │
│  │   ╱    ╲──╯  ╲╱    ╲╱    ╲                       │        │
│  │  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ (previous, dashed)    │        │
│  │  Apr 1   Apr 8    Apr 15   Apr 22   Apr 29       │        │
│  └──────────────────────────────────────────────────┘        │
└──────────────────────────────────────────────────────────────┘
```

**Trend chart.** Recharts `<LineChart>`. Two `<Line>` series when overlay is on (this period solid, previous period dashed). For per-restaurant breakdown, the analyst goes to the Comparison page (§9.5) — keeping that concern there avoids two pages doing the same thing.

**Granularity rule:** auto-pick a sensible default based on date range, but always overridable.

| Range | Default granularity |
|---|---|
| ≤ 2 days | Hour |
| 3–60 days | Day |
| 61–365 days | Week |
| > 365 days | Month |

**SQL (day granularity, revenue metric):**

```sql
SELECT
  (b.sold_at AT TIME ZONE :chain_tz)::date AS bucket,
  COUNT(*)     AS bills,
  SUM(b.total) AS revenue,
  AVG(b.total) AS avg_ticket
FROM bills b
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
GROUP BY bucket
ORDER BY bucket;
```

For other granularities, swap the bucket expression:
- Hour: `date_trunc('hour', b.sold_at AT TIME ZONE :chain_tz)`
- Week: `date_trunc('week', b.sold_at AT TIME ZONE :chain_tz)::date`
- Month: `date_trunc('month', b.sold_at AT TIME ZONE :chain_tz)::date`

### 9.4 Peak Hours (`/peak-hours`)

**Wireframe:**

```
┌──────────────────────────────────────────────────────────────┐
│  Peak Hours — Last 30 days, all restaurants                  │
├──────────────────────────────────────────────────────────────┤
│  View: [• Heatmap   ◯ Hourly bars]   Metric: [• Bills  ◯ Rev]│
│  (Restaurant filter is global — see filter bar above)        │
├──────────────────────────────────────────────────────────────┤
│        00 02 04 06 08 10 12 14 16 18 20 22                   │
│   Mon  ░  ░  ░  ░  ░  ▒  ▓  █  ▓  ▒  ▒  ░                    │
│   Tue  ░  ░  ░  ░  ░  ▒  ▓  ▓  ▒  ▒  ▒  ░                    │
│   Wed  ░  ░  ░  ░  ░  ▒  ▓  █  ▓  ▒  ▒  ░                    │
│   Thu  ░  ░  ░  ░  ░  ▒  ▓  █  ▓  ▒  ▒  ░                    │
│   Fri  ░  ░  ░  ░  ░  ▒  ▓  █  ▓  ▒  ▓  ▒                    │
│   Sat  ░  ░  ░  ░  ░  ▒  ▓  █  █  ▓  ▓  ▒                    │
│   Sun  ░  ░  ░  ░  ░  ▒  ▓  █  ▓  ▒  ▒  ░                    │
│                                                              │
│   Legend: ░ low  ▒ medium  ▓ high  █ peak                    │
└──────────────────────────────────────────────────────────────┘
```

**View 1: heatmap.** 7 rows (Mon–Sun) × 24 columns (00–23). Each cell colour-mapped to the bills (or revenue) count for that DOW × hour combination. Continuous colour scale (light → dark). Hover tooltip shows exact value.

Recharts has no native heatmap. Implementation: build it as a 7×24 `<svg>` grid with `<rect>` per cell, or use a `<BarChart>` per row with stacked single-cell bars. The svg approach is cleaner.

**View 2: hourly bars.** Same data aggregated across days — one bar per hour 00–23. Recharts `<BarChart>`. Useful when the analyst wants the simple "what's our busiest hour overall" answer.

**SQL (heatmap):**

```sql
-- Bill-level aggregation: category filter does NOT apply (see §8 filter matrix)
SELECT
  EXTRACT(DOW  FROM b.sold_at AT TIME ZONE :chain_tz)::int AS dow,   -- 0=Sun..6=Sat
  EXTRACT(HOUR FROM b.sold_at AT TIME ZONE :chain_tz)::int AS hour,
  COUNT(*)     AS bills,
  SUM(b.total) AS revenue
FROM bills b
WHERE b.sold_at >= :from
  AND b.sold_at <  :to
  AND b.restaurant_id = ANY(:restaurant_ids)
GROUP BY dow, hour
ORDER BY dow, hour;
```

The frontend pivots this into a 7×24 matrix. Empty cells (no bills that DOW/hour) get value 0 and the lowest colour shade. Frontend reorders rows so Monday appears first (PostgreSQL's `EXTRACT(DOW)` returns 0 for Sunday).

**SQL (KPI matrix):**

The earlier draft of this query used correlated subqueries for `top_item` and `peak_hour`, which fan out to 2 × N subaggregations across N restaurants. At 6 restaurants × 1 year of data, that's measurably over the 1.2s budget. CTE rewrite below scans `bills` once and `bill_items` once, regardless of restaurant count.

```sql
WITH bill_agg AS (
  -- One pass over bills, aggregating per restaurant
  SELECT
    b.restaurant_id,
    COUNT(*)     AS bills,
    SUM(b.total) AS revenue,
    AVG(b.total) AS avg_ticket
  FROM bills b
  WHERE b.sold_at >= :from
    AND b.sold_at <  :to
    AND b.restaurant_id = ANY(:restaurant_ids)
  GROUP BY b.restaurant_id
),
peak_hour_agg AS (
  -- For each restaurant, pick the hour-of-day with the most bills
  SELECT DISTINCT ON (b.restaurant_id)
    b.restaurant_id,
    EXTRACT(HOUR FROM b.sold_at AT TIME ZONE :chain_tz)::int AS peak_hour
  FROM bills b
  WHERE b.sold_at >= :from
    AND b.sold_at <  :to
    AND b.restaurant_id = ANY(:restaurant_ids)
  GROUP BY b.restaurant_id, EXTRACT(HOUR FROM b.sold_at AT TIME ZONE :chain_tz)
  ORDER BY b.restaurant_id,
           COUNT(*) DESC,
           EXTRACT(HOUR FROM b.sold_at AT TIME ZONE :chain_tz) ASC  -- tie-break: earliest hour
),
top_item_agg AS (
  -- For each restaurant, pick the menu item with the most quantity sold
  SELECT DISTINCT ON (b.restaurant_id)
    b.restaurant_id,
    m.name AS top_item
  FROM bill_items bi
  JOIN bills      b ON b.id = bi.bill_id
  JOIN menu_items m ON m.id = bi.menu_item_id
  WHERE b.sold_at >= :from
    AND b.sold_at <  :to
    AND b.restaurant_id = ANY(:restaurant_ids)
  GROUP BY b.restaurant_id, m.id, m.name
  ORDER BY b.restaurant_id,
           SUM(bi.quantity) DESC,
           m.id ASC                                -- tie-break: lower menu_item_id
)
SELECT
  r.id,
  r.name,
  r.city,
  COALESCE(ba.bills, 0)       AS bills,
  COALESCE(ba.revenue, 0)     AS revenue,
  ba.avg_ticket               AS avg_ticket,    -- NULL if no bills, frontend renders "—"
  ti.top_item                 AS top_item,      -- NULL if no bills
  ph.peak_hour                AS peak_hour      -- NULL if no bills
FROM restaurants r
LEFT JOIN bill_agg      ba ON ba.restaurant_id = r.id
LEFT JOIN peak_hour_agg ph ON ph.restaurant_id = r.id
LEFT JOIN top_item_agg  ti ON ti.restaurant_id = r.id
WHERE r.id = ANY(:restaurant_ids)
ORDER BY revenue DESC NULLS LAST;
```

The frontend's "highest = green tint, lowest = red tint" rule (§9.5 wireframe) only considers non-NULL values — a restaurant with zero bills shows an em-dash in `avg_ticket`, `top_item`, `peak_hour` and is excluded from the highlight comparison for those rows.

For the daily trend chart, run the §9.3 day-granularity query with `GROUP BY restaurant_id, bucket` and one `<Line>` per restaurant in Recharts.

## 10. Cross-cutting Concerns

### 10.1 Filter behaviour

- Filter state lives in URL query string. Every page reads from URL on mount and writes to URL on change. Shareable links work for free.
- Date range presets: Today, Yesterday, Last 7d (default), Last 30d, MTD, Last 90d, YTD, Custom.
- Restaurant filter: multi-select with "All" toggle. Default = all.
- Category filter: multi-select with "All" toggle. Default = all. Categories come from `DISTINCT menu_items.category`.
- "Reset" button restores defaults.

### 10.2 Empty / loading / error states

Every chart and table has three non-happy-path states. A page is not done until all three are designed.

| State | When | What the user sees |
|---|---|---|
| Loading | Query in flight | Skeleton placeholder matching the chart's shape (grey boxes for KPI cards, an animated bar grid for charts, a striped table for tables). Never a spinner-only screen. |
| Empty | Query returned 0 rows | "No bills sold in this range." Plus a hint: "Try widening the date range or selecting different restaurants." |
| Error | API returned non-2xx or threw | "Couldn't load this view." Plus the request ID for support. Plus a "Retry" button. Errors do **not** crash the whole dashboard — each panel fails in isolation. |

### 10.3 Performance budgets

| View | p90 query budget | p90 page render budget |
|---|---|---|
| Overview KPIs (each) | 200 ms | — |
| Overview trend | 400 ms | — |
| Best Sellers (Top 100) | 500 ms | — |
| Time Series (year, day-grain) | 800 ms | — |
| Peak Hours heatmap (year) | 600 ms | — |
| Comparison (6 restaurants, year) | 1,200 ms | — |
| **Whole page (network + render)** | — | **< 2 s (PRD §8)** |

If we miss budgets at scale, the next move (V2) is a daily-rollup table refreshed by the sync runner — but indexes alone should hit budget at PRD's stated 5,000 bills/day.

### 10.4 Indexes required

The PRD §8 mentions the date predicate index. The dashboard needs more than that. **PostgreSQL does not auto-index foreign-key columns**, so even though `bill_items.bill_id` and `bill_items.menu_item_id` are FKs, neither has a B-tree index by default. All three of these need to exist before the dashboard ships:

```sql
-- Date-range + restaurant predicates (likely already in PRD migrations)
CREATE INDEX IF NOT EXISTS ix_bills_restaurant_sold_at
  ON bills (restaurant_id, sold_at);

-- Bill-line joins (NOT auto-created by FK)
CREATE INDEX IF NOT EXISTS ix_bill_items_bill_id
  ON bill_items (bill_id);
CREATE INDEX IF NOT EXISTS ix_bill_items_menu_item_id
  ON bill_items (menu_item_id);

-- Category filter on Best Sellers and Overview top-item
CREATE INDEX IF NOT EXISTS ix_menu_items_category
  ON menu_items (category);
```

**Verify before shipping** — run `EXPLAIN (ANALYZE, BUFFERS)` on the year-of-data version of the heaviest queries (Time Series day-grain, Comparison KPI matrix). If the planner picks a sequential scan on `bills` for a year-long range, the index either is missing or has low selectivity, and the budget in §10.3 is at risk.

### 10.5 Auth and authorization

Every dashboard page requires login (PRD §8). Operations and analysts have read access to all restaurants — no per-restaurant gating in V1. Auth is owned by the API service, not the dashboard; the dashboard just sends the session cookie/token with every request.

### 10.6 Export (V1, deferrable)

CSV export is **not** in PRD requirements — it's a quality-of-life addition this design proposes. If schedule is tight, defer to V1.1 without affecting the rest of the doc.

When shipped: every table view has an "Export CSV" button. The export endpoint runs the same SQL the page uses (with the LIMIT removed where appropriate) and streams CSV to the browser. The pattern from the existing `tortilla_shops_reports/` CSV generator can be reused.

**Row cap:** export is hard-capped at **100,000 rows**. If a query would return more, the API returns a 413 with a hint to narrow the date range. This protects the API from accidental year-of-bills exports (~1.8M rows) that nobody actually wants in a single CSV.

### 10.7 Date range validation

The API rejects ranges where `from >= to` (400 Bad Request). It also rejects ranges longer than **2 years** (400 Bad Request) — anything longer should be a separate report run, not a dashboard query. The frontend's date-range picker enforces the same upper bound so the user never hits the API error.

### 10.8 Per-panel error isolation

The dashboard never crashes whole-page on a single API failure. Each chart and table is its own React error boundary; a failed panel renders the §10.2 error state in place while the rest of the page continues working. No caching or retry layer in V1 — defer to V2 when the dashboard becomes a high-traffic surface.

### 10.9 Timezone display

All timestamps in the database are UTC (PRD `timestamptz`). The dashboard renders dates and hour-of-day in the **chain timezone** (config value, V1 default `Europe/Madrid`). The chosen timezone is shown subtly in the filter bar so analysts know what "13:00" means.

## 12. Open Questions

1. **Chain timezone — config or env var?** PRD §10 lists timezone as open. Recommend a single config value (`CHAIN_TZ=Europe/Madrid`) read at API startup, surfaced in the filter bar.
2. **Day-of-week first day.** EXTRACT(DOW) returns 0=Sun. Most European users expect Monday first. Frontend should re-order rows when rendering.
3. **CSV export size cap.** A year of bills is ~1.8M rows. Cap export at 100k rows? Stream all? Recommend: stream all, but show a warning in the UI when > 100k.
4. **"Top item" ties.** What if two items have the same quantity? Pick the lower `menu_item_id` for stability (deterministic tie-break). Worth specifying so the test expectations match.
5. **Refunds / voids.** PRD §10 flags this as the question most likely to bite us. The dashboard's revenue numbers are only as honest as the adapter layer makes them. Recommend: `bill_items.line_total` is the source of truth; the adapter is responsible for emitting negative-quantity rows on refund. The dashboard sums whatever it gets.
6. **"Best seller" ranking when restaurants have wildly different sizes.** A 1,200-bill/day restaurant can dominate "best seller across the chain" rankings. Recommend: V1 just sums absolute quantities; if it becomes an issue, V2 adds a "normalized per-restaurant" toggle.
